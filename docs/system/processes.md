# Processes

This document describes the five end-to-end flows of the built system as traced through the CLI commands, the application stages and the host, hook, GSD, graphify and git adapters (`src/cli/`, `src/app/`, `src/adapters/`, `src/hook/`). Two belong to onboarding: `avarice onboard` on a brownfield repository, and `avarice resume` after a kill during the map invocation. Three belong to the unattended run: `avarice start` taken to ready for review, a kill during the unit followed by `avarice resume`, and a crashed unit that is discarded and retried once.

Onboarding is one lease-holding pass through a fixed list of stages. The first stage that cannot proceed stops it in a named state: incompatible when GSD is missing or out of range, blocked when the host cannot enforce containment or a budget is spent. It is also blocked when validation fails twice or the staging tree holds writes outside every write set. An index that cannot be built never stops it. A kill leaves the host running and the lease held, so resume works only after the lease expires. It then ends the host by its session ID, lets the files in staging decide whether the map invocation finished, and either validates them or launches the map again.

A run has the same shape with a different payload. `start` stores a contract and hands the run to a detached supervisor, which holds a lease and works through three stages: preparation, the unit, and the final proof with the hand-off. The run stops in `ready_for_review` or `blocked_on_decision`. A blocked run is final in practice, because no command answers a decision. A kill leaves the run in its committed state and a host that may still run. Resume ends that host before it reads anything from the clone. The leaf for the run mechanisms is [runs.md](runs.md); the flows below only put its steps in order.

The points to watch where two documents meet are listed under "Things to look out for at the hand-offs".

## Onboard a brownfield repository

The flow is drawn in [onboard.puml](diagrams/onboard.puml). The command ends with exit 0 only when the project is active; every other ending is exit 3, and a failure of the run itself is exit 70 ([cli-reference.md](cli-reference.md#onboard)).

1. The operator runs `avarice onboard --policy onboarding` with the repository path. Flags are checked first, so a bad mode or a malformed budget registers nothing ([cli-reference.md](cli-reference.md#onboard)).
2. Startup opens the ledger, locates GSD and the graphify binary, and chooses the host. The contained host is chosen only when an admitted GSD, a `claude` executable, the GSD shim preamble, the hook script, a working sandbox and an admitted host version are all present. Otherwise a refusing host is used, and the reason is stored in its descriptor ([integrations.md](integrations.md#the-unavailable-host-fallback), [config-reference.md](config-reference.md)).
3. Registration and preflight read the repository from git objects at HEAD, pin that commit, and record names and classifications only. An active record, or another onboarding past its first state, refuses the command with exit 3. An onboarding still at its first state is continued, not duplicated ([onboarding.md](onboarding.md#preflight-and-refusals)).
4. The command takes the lease on the onboarding and starts the stage loop ([onboarding.md](onboarding.md#stage-loop-and-leases)).
5. Contract stage: GSD must be present and in range, otherwise the onboarding ends incompatible before any contract or staging exists. Then the contract is compiled, stored with its budget rows, and the onboarding moves to the contract-proposed state ([onboarding.md](onboarding.md#contract-compilation-and-budgets)).
6. Workspace stage: a local clone is made at the pin under the work root, GSD is probed, the mapping mode is decided, and GSD is configured in staging. Then the host's declared enforcement is read. A host that does not report enforced ends the onboarding blocked with reason enforcement failure, with the clone and the GSD settings already in place and no map launch made ([onboarding.md](onboarding.md#staging), [onboarding.md](onboarding.md#enforcement-check)).
7. Map stage: unless the mode is skip, the invocation budget is reserved. The reservation is one invocation unit, the smaller of the wall-clock share and what remains, and the smaller of the per-invocation cap and the remaining cost. The launch is then recorded as started with a fresh session ID. A refused reservation ends the onboarding blocked with reason budget exhausted ([onboarding.md](onboarding.md#mapping), [containment.md](containment.md#budgets-and-reservations)).
8. Launch assembly generates five inputs in a private directory, proves the launch checks and judges the launch line. It then starts the host detached in its own process group with a scrubbed environment, and AVARICE enforces the wall clock. Any refusal before the spawn blocks the onboarding with reason enforcement failure ([containment.md](containment.md#how-a-launch-is-assembled), [integrations.md](integrations.md#claude-code)).
9. During the run, every tool call goes through the PreToolUse hook. An allowed call is charged to the shared run budget in the same ledger transaction that records the decision: tool calls for ordinary tools, the subagent total for agent calls. A denied call is charged nothing. A call that finds its budget spent is denied as budget exhausted ([containment.md](containment.md#the-pretooluse-hook)).
10. When the host exits, the invocation settles in one ledger transaction: the unit, the measured duration and the cost are charged, and the transcript is stored redacted. The cost is the one the host reported, except for an ending without a result, a signal or the wall clock, which is charged at least the cost reservation. The ending is classified from measured facts, never from model text. A hook deny for a spent budget during the invocation overrides the host's own outcome ([onboarding.md](onboarding.md#mapping), [integrations.md](integrations.md#outcome-classification)).
11. AVARICE stamps the map itself through GSD after progressed, no-progress and inconclusive endings, because the mapper's own stamp call is denied by the hook. Progressed and inconclusive endings go to validation; denied, failed and no-progress endings block with reason decision; budget exhausted blocks with that reason ([onboarding.md](onboarding.md#mapping)).
12. Validation runs seven checks over the staging map. Accepted moves on. A secret hit blocks at once. Any other failure sends the onboarding back to mapping once and then blocks ([onboarding.md](onboarding.md#validation-and-the-retry-rule)).
13. The three index steps run in order: code graph, intel, knowledge. graphify is run by AVARICE through the sandboxed executor, never from the host. Intel and knowledge each take one more contained invocation under the same hook and budgets, and AVARICE then finishes each step itself. A step that fails is recorded as absent with a reason and never blocks ([indexes-and-context.md](indexes-and-context.md#the-index-steps)).
14. Activation re-checks the whole staging diff against the write sets, stores the map documents and a manifest, and inserts the project record and moves to active in one ledger transaction ([onboarding.md](onboarding.md#activation), [data-model.md](data-model.md#project-record)).

## Kill during the map invocation, then resume

The flow is drawn in [resume-after-kill.puml](diagrams/resume-after-kill.puml).

1. The supervisor is killed with no cleanup. The launch row stays started with its session ID, one invocation unit stays reserved, and the lease stays recorded until it expires. The host runs on detached, and the hook keeps charging the run's tool-call budget for calls the orphan makes ([containment.md](containment.md#session-id), [data-model.md](data-model.md#leases-and-optimistic-concurrency)).
2. The operator runs `avarice resume` with the onboarding ID. A stopped onboarding is reported without taking the lease. A live lease refuses the command with exit 3; `status` shows the onboarding as interrupted once the lease is absent or expired. The lease lasts up to 180 seconds after its last renewal, so the orphan can run for that long before anything can end it ([cli-reference.md](cli-reference.md#resume), [onboarding.md](onboarding.md#stage-loop-and-leases)).
3. Once the lease has expired, the takeover succeeds and raises the fence, so a late write from the dead holder is refused ([data-model.md](data-model.md#leases-and-optimistic-concurrency)).
4. Reaping comes first. Every launch row left started is looked up by its session ID in the process table; the whole process group is terminated, then killed after a grace period. A process that survives, or a failed search, fails the resume with exit 70 and leaves every row started. A host without a reap capability skips this step silently ([integrations.md](integrations.md#reaping-by-session-id), [onboarding.md](onboarding.md#resume-reconcile-and-reaping)).
5. Reconcile reads the map files in staging. If more launches than validations exist and every required file is present, the launch is marked reconciled, AVARICE stamps the map, and the onboarding goes to validation with no second launch. Otherwise the launch is marked interrupted and the map stage launches again ([onboarding.md](onboarding.md#resume-reconcile-and-reaping)).
6. The next reservation converts the dead reservation to spent, charging it the cost it was allowed to use, and appends a warning event. No wall-clock time is charged for it, and nothing is refunded, including tool calls the orphan made. In the reconciled branch the next reservation is the intel invocation. In the relaunch branch it is the map relaunch, with a new session ID ([containment.md](containment.md#budgets-and-reservations)).
7. The loop continues as in the onboard flow from validation (or from the relaunched map) to activation. Registration, the contract and the workspace stage do not run again, because the committed state is already past them ([onboarding.md](onboarding.md#resume-reconcile-and-reaping)).

## Start a run and take it to ready for review

The flow is drawn in [run-to-ready.puml](diagrams/run-to-ready.puml). A run needs a repository that is already onboarded to an active record. The command exits 0 once the run is stored and its supervisor started; with `--wait`, it exits 0 only when the run reaches ready for review. A start rule that refuses the run gives exit 3, as does any other stop state under `--wait`. A usage error is exit 64, and an internal failure is exit 70 ([cli-reference.md](cli-reference.md)).

1. The operator runs `avarice start` with a brief file and the policy `routine`. Flags are checked before the profile is resolved, so a usage error leaves nothing on disk ([cli-reference.md](cli-reference.md)).
2. The start service runs its checks in a fixed order and creates nothing until all have passed: the policy, an admitted GSD, the brief, the project, the preflight and the contract compile. The preflight reads only git objects, so an uncommitted edit cannot change an answer. The compile fixes the run's authority and only narrows it, and it includes the static half of gate G0 ([runs.md](runs.md#order-of-checks-and-the-refusals), [runs.md](runs.md#the-contract)).
3. One ledger transaction stores the run as `contract_ready`, contract version 1, the budget rows and the single work item. The contract file is then written through a temporary file and a rename, and a `start:preflight` step records the pin, the HEAD and the brief digest ([runs.md](runs.md#what-a-successful-start-stores), [data-model.md](data-model.md)).
4. The command spawns the supervisor detached, in its own process group, and records its PID as a step. A refused spawn exits 70 and leaves the stored run in `contract_ready`. Without `--wait` the command exits 0 here. With `--wait` it polls the ledger every 250 milliseconds ([runs.md](runs.md#the-detached-supervisor)).
5. The supervisor takes the run lease and rewrites the contract file when a killed start left it missing. It runs the resume prelude (a fresh run has nothing to reap), then loops over the stage registered for the committed state until a stop state ([runs.md](runs.md#supervisor-and-lease), [onboarding.md](onboarding.md#stage-loop-and-leases)).
6. Preparation runs six actions, each preceded by its checkpoint, and skips an action whose step is already completed. They are the clone, the GSD settings, the dependency install, the check validation, the baseline and the enforcement check. The baseline opens the run's first attempt. A decision or containment condition in any action blocks the run; the enforcement check blocks without opening a decision record. A pass moves the run to `running` and records the clone and branch ([runs.md](runs.md#preparation-contract_ready), [checks-and-evidence.md](checks-and-evidence.md)).
7. The unit stage builds a context pack of references, delegates the item, snapshots the clone and reserves the invocation budget. The launch step is recorded as started with a session ID before the host is called. A spent budget blocks the run with the host never called ([runs.md](runs.md#the-unit-running), [containment.md](containment.md#budgets-and-reservations)).
8. The host runs the GSD quick unit detached in its sandbox, and every tool call goes through the PreToolUse hook as in the onboard flow. When the host exits, the invocation settles and the supervisor classifies the ending from facts it measured in the clone and the unit's records, not from the host's own outcome ([containment.md](containment.md#the-pretooluse-hook), [runs.md](runs.md#the-unit-running)).
9. Only a progressed unit continues. A crash or timeout with an unmoved HEAD is discarded and retried once, which is the last flow below. Every other ending opens a decision record and blocks the run, with a reason and class chosen by the ending ([runs.md](runs.md#decisions)).
10. Gate G2 judges the unit against the contract's scope and the baseline. The required checks run on the working tree only when every other rule passes. A failed G2 blocks the run before any commit ([checks-and-evidence.md](checks-and-evidence.md), [runs.md](runs.md#gate-g2-and-the-commit)).
11. A passing G2 moves the item to gated. The supervisor archives the unit's records, takes every artifact path out of the clone, and commits only the in-scope paths with run and attempt trailers. The item is done and the run moves to `verifying` ([runs.md](runs.md#gate-g2-and-the-commit)).
12. The final proof runs the required and target checks at the committed revision, stores the GSD verifier's verdict as model-review evidence, and judges gate G4. A failed G4 blocks the run with no repair item and no second attempt ([runs.md](runs.md#final-proof-and-hand-off-verifying), [checks-and-evidence.md](checks-and-evidence.md)).
13. The hand-off fetches the run branch into the source repository as one new local ref, create-only and never forced. The step and a hand-off event are recorded, the attempt ends handed-off, and the run moves to `ready_for_review` only because a passed G4 row exists for exactly that commit. The supervisor releases the lease and exits 0 ([runs.md](runs.md#final-proof-and-hand-off-verifying)).
14. The operator reads the result with `status` and `inbox`, which read the ledger and change nothing. Nothing was pushed or merged, and the user's checkout was never written ([runs.md](runs.md#status-and-inbox)).

## Kill during the unit, then resume a run

The flow is drawn in [run-resume-after-kill.puml](diagrams/run-resume-after-kill.puml). It is the run counterpart of the onboarding resume. The command sits in the same place, but the reconcile reads the run's attempt and the clone's HEAD instead of the map files.

1. The supervisor is killed with no cleanup while the unit runs. The run stays `running` and the item stays delegated. The launch row stays started with its session ID, one invocation unit stays reserved, and the lease stays recorded until it expires. The host runs on detached, and the hook keeps charging the run budget ([runs.md](runs.md#resume-and-reconcile), [containment.md](containment.md#session-id)).
2. Once the lease has lapsed, `status` presents the run as paused (supervisor interrupted), and `start --wait` prints an interrupted line with the resume command and exits 3. This is presentation only: the ledger state is still `running` ([runs.md](runs.md#status-and-inbox)).
3. The operator runs `avarice resume` with the run ID. A run in a stop state is only reported, with no lease taken. A live lease refuses the command with exit 3 and changes nothing. Otherwise the command prints the state and next action it resumes from, names the interrupted step and, when an attempt was open, the attempt, spawns a detached supervisor and records a resume step ([cli-reference.md](cli-reference.md#resume), [runs.md](runs.md#resume-and-reconcile)).
4. The new supervisor takes the lease, which raises the fence, and runs the prelude. Reaping comes first. Every launch row left started is ended by its session ID before any row is marked or anything is read from the clone. A failed reap stops the resume with every row still started and records a failed reconcile step, and `resume --wait` then exits 70. A host without a reap capability skips the end step, and the rows are still marked interrupted ([integrations.md](integrations.md#reaping-by-session-id), [runs.md](runs.md#resume-and-reconcile)).
5. The orphaned reservation is spent at once, at the cost it was allowed, with no wall-clock time charged and nothing refunded ([containment.md](containment.md#budgets-and-reservations)).
6. The reconcile pauses the run (a real transition, with reason interrupted) and reads the item. If the clone HEAD moved under the delegated item, the run blocks with enforcement failure and a containment finding, and nothing is discarded. If the launch step names the attempt, the attempt is recorded as inconclusive, unless it was already classified, and the item takes the discard and retry road. If the interrupted attempt was already the retry, the run blocks with a decision naming both attempts. If the invocations budget cannot cover another unit, the run blocks with budget exhausted ([runs.md](runs.md#resume-and-reconcile)).
7. An attempt with no launch step ran nothing. The clone goes back to its snapshot when one exists, the item goes to ready, and the retry is not used.
8. After a retry or a no-op reconcile, the run goes back to `running` and the stage loop continues with a new attempt, as in the first flow from the context pack onward ([runs.md](runs.md#discard-and-the-one-retry)).

A kill at a later point reconciles differently. A kill after the item is gated leaves it gated. If the commit was already made and the clone HEAD carries this run's and this attempt's trailers, the commit step is recorded and no second commit is made. If it was not made, the stage makes it. A kill during the final proof leaves the run `verifying`, shown as paused (verification interrupted). The required checks that never finished get inconclusive evidence, and the run resumes at the checks or, when G4 already passed for this commit, at the hand-off. A kill between the fetch and its record repeats the fetch, which is idempotent ([runs.md](runs.md#resume-and-reconcile)).

## A crashed unit, discarded and retried once

The flow is drawn in [run-discard-retry.puml](diagrams/run-discard-retry.puml). It involves no kill and no resume: the supervisor lives, and the host ends badly.

1. The unit ends with no result, a signal or a non-zero exit, or the wall clock fires. The invocation settles, and a unit that ended without a result, by a signal or by the wall clock is charged at least its cost cap. The supervisor measures the clone and records the classification, which is inconclusive or failed ([runs.md](runs.md#the-unit-running)).
2. Routing checks the endings in a fixed order. A moved HEAD blocks the run with enforcement failure and a containment finding, and no recovery touches the clone. A loop limit, a spent budget, a pause, a denial, no progress or an error result with exit 0 each block with their own reason and are never retried ([runs.md](runs.md#the-unit-running)).
3. A crash or timeout with an unmoved HEAD and no other host error is retried while the item has a retry left. A host error other than a timeout is never retried. An unavailable or denying host blocks with enforcement failure, and any other host error blocks with a decision ([runs.md](runs.md#discard-and-the-one-retry)).
4. Before the discard, the invocations budget must cover another unit, counting the killed unit's charge. If it cannot, the run blocks with budget exhausted and nothing is discarded ([runs.md](runs.md#discard-and-the-one-retry)).
5. The discard commits its checkpoint first, which carries the lease fence, so a stale supervisor cannot reach the restore. The clone's changed paths go back to the snapshot taken right before the launch, and ignored paths are not touched. An added path is removed only as a file or link. If the HEAD moved by then, the discard is refused with nothing changed and the run blocks with enforcement failure ([runs.md](runs.md#discard-and-the-one-retry)).
6. The discard step records what was restored, removed and left, with side effect none. The attempt ends discarded and the item goes back to ready. A unit has no network, no push and no change request, so there is no outside effect to roll back ([runs.md](runs.md#discard-and-the-one-retry)).
7. The retry attempt starts without a second context-pack checkpoint, rebuilds the pack, delegates the item, snapshots the clone and launches again. If it progresses, the run continues as in the first flow from gate G2. If it crashes or times out again, the run blocks with a decision naming both attempts and how each ended. Any other ending routes as it did the first time ([runs.md](runs.md#discard-and-the-one-retry)).

## Things to look out for at the hand-offs

- **Where an unavailable host stops the run.** A missing GSD stops at the contract stage as incompatible. A missing or unusable host does not: the contract stage passes, the clone and GSD configuration are made, and the workspace stage then blocks with reason enforcement failure ([onboarding.md](onboarding.md#enforcement-check), [integrations.md](integrations.md#the-unavailable-host-fallback)).
- **graphify and the host.** The host's search path never includes graphify. The knowledge pass runs no shell and no skill, and AVARICE runs graphify itself for the code graph and for clustering ([config-reference.md](config-reference.md), [indexes-and-context.md](indexes-and-context.md#the-knowledge-pass)).
- **Who charges what.** The application layer charges invocations, wall clock and cost, around each invocation. The hook charges tool calls and subagents during it. All five budgets are per run, shared by the map, intel and knowledge invocations and by a resumed run ([containment.md](containment.md#budgets-and-reservations)).
- **The concurrency deny is not a budget deny.** A subagent refused for concurrency is recorded as a hook deny but does not count as budget exhausted, so it never overrides an outcome ([containment.md](containment.md#subagent-limits)).
- **Resume cannot reap before the lease expires.** A resume inside the window exits 3 and ends nothing, for an onboarding and for a run alike ([onboarding.md](onboarding.md#stage-loop-and-leases)).
- **Reconcile judges presence, not quality.** It decides from the required files existing; validation then judges their content ([onboarding.md](onboarding.md#resume-reconcile-and-reaping)).
- **Resume with a refusing host.** The reap is skipped, so a survivor from an earlier environment is not ended before the staging files are read. A needed relaunch is refused by the host and surfaces as a failed run (exit 70), not as a block. The invocation unit is spent each time ([integrations.md](integrations.md#reaping-by-session-id)).
- **A stored run with no supervisor.** A start killed after its transaction leaves a run without its contract file, and a refused spawn leaves a run that nobody supervises. Both stay `contract_ready`. `resume` or `supervise` continues them, and the supervisor rewrites a missing contract file before it launches anything ([runs.md](runs.md#the-detached-supervisor)).
- **A blocked run is the end of the line.** Every flow above that ends in a block ends there, because no command answers a decision and `resume` only reports a blocked run. A block at the enforcement check also opens no decision record, so the inbox shows nothing for it; the run's state and reason are the only trace ([runs.md](runs.md#decisions)).
- **Paused is two different things.** The ledger state `paused` is entered only by a resume reconcile, and a reconcile that is killed leaves it there. The `paused (supervisor interrupted)` and `paused (verification interrupted)` lines in `status` show a stopped supervisor, with the ledger state unchanged ([runs.md](runs.md#status-and-inbox)).
- **The retry is counted per launch.** An attempt that never launched a unit does not use the one retry, in a resume or otherwise ([runs.md](runs.md#resume-and-reconcile)).
- **The commit is the supervisor's alone.** A moved clone HEAD is a containment breach in the unit, in the discard and in the reconcile. The one exception is a commit carrying this run's and this attempt's trailers, found at a gated item ([containment.md](containment.md#git-safety)).
- **Kills are tested at 24 points.** A fault suite with a fake host kills the run supervisor at 24 named points across the three stages. It resumes each and compares the result with an uninterrupted run. The point between the fetch and its record is one of them.
