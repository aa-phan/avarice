## How this plan runs

The executor has no Agent tool, so it cannot spawn agents. The orchestrator does every agent fan-out. Tasks 2, 4 and 6 are `checkpoint:orchestrator-dispatch` tasks. The executor stops at each one and returns `## CHECKPOINT REACHED` with `type: orchestrator-dispatch`, and the orchestrator, not the owner, resolves it. The orchestrator spawns the agents named in the task's `ORCHESTRATOR-DISPATCHED` lines, persists what they return, runs the task's verify commands and resumes the executor at the next task. No task needs the owner. The only owner contingency is a document that fails review twice (Task 7, step A).

| Task | Run by | Does |
|---|---|---|
| 1 | executor | Worklist: dispatch list, code-surface map, packets, findings candidates, denominators |
| 2 | orchestrator | Tracer grounding: one doc-grounder for runs.md |
| 3 | executor (tracer) | runs.md lands end to end: document, both README tables, coverage, findings, unknowns |
| 4 | orchestrator | Tracer review of runs.md, brief corrections, then one doc-grounder per remaining document |
| 5 | executor | Tracer fixes and runs.md marked reviewed; every other package landed and assembled |
| 6 | orchestrator | One fresh prose-reviewer per remaining new or changed document |
| 7 | executor | Review fixes, documents marked reviewed, coverage recount, final gates |

Tracer slice: runs.md is the largest new document and the riskiest. Task 1 is its inventory prerequisite. It is grounded in Task 2, landed in Task 3 (the `type="tracer"` task, the first one that puts the slice into the tree), reviewed in Task 4 and marked reviewed in Task 5. No other grounder starts until the runs.md review verdict is in and its systemic findings are folded into the brief.

Working files, all under `.planning/phases/02-contained-unattended-run-of-one-work-item/` (written `$P` below):
- `$P/02-23-doc-worklist.md`: the worklist (Task 1); its dispatch lines drive every later task.
- `$P/02-23-grounding/<stem>/`: one package per grounded document, written by its grounder. It holds document.md, findings.md, unknowns.md, coverage.md and seams.md, plus `diagrams/*.puml` when the packet asks for diagrams. Also `$P/02-23-grounding/brief-amendments.md` (Task 4).
- `$P/02-23-reviews/<stem>.md`: one report per reviewed document, written by the orchestrator. Line 1 is `Reviewed: docs/system/<file> sha256 <digest> at <commit>`, line 2 is `Verdict: <the reviewer's first line>`, then comes a blank line and the report verbatim. An `## Answers` section is appended by the executor when it answers a finding rather than applying it.

Stems are lowercase file stems (`readme` for README.md). The executor commits with the `docs(02-23): ...` subject form, which the subject-keyed scope gates rely on. A second scope gate does not depend on the subject: it reads the worklist's `Plan base:` line (written once in Task 1, never changed) into `/tmp/02-23-base.txt` and runs `git diff --name-only <plan base>..HEAD` against the same allowlist, so a commit with any other subject that touches code or a proposal is still caught.
