## How the campaign ran, and where it departs from the skill's text

* **Probed in scratch clones, not in the working tree.** The skill recommends one fresh clone per worker. Two clones of the scanned commit under `$TMPDIR` ran the probe (shards A and B), so the working tree never held a mutation: `git diff --exit-code -- src` in the working tree stayed clean the whole time, and the pre-existing suite stayed untouched while pass 1 ran, which keeps the attribution (the test that killed each mutant is the test that existed at the scanned commit).
* **Suite command.** The plan's command, `node --test "test/unit/**/*.test.ts" "test/integration/**/*.test.ts" "test/containment/executor.test.ts" "test/containment/failclosed.test.ts" "test/fault/**/*.test.ts" "test/mutation/**/*.test.ts"`, with `AVARICE_LIVE` unset and no `test/containment/live-*.test.ts`, was the baseline (908 tests passed on the scanned commit). The probe itself ran `node .mutation-test/suite-runner.mjs`, a wrapper over exactly the same file set. It runs each test file as its own `node --test <file>` (the isolation `node --test` gives a file anyway) in a pool, runs first the files that mention the mutated module, ends the run on the first failing file, and reruns a failing file once on its own before the failure counts (a kill must reproduce). The reason was cost: the full suite takes about 95 s, and 249 definitions at that price did not fit. A rerun that passed is logged to `.mutation-test/flakes.log` (the entries came from `claude-host.test.ts` under Findings MF-01 and from `lease.test.ts` under Observation O-2). The wrapper prints `N passed; M failed` for the probe's proof pattern; a green full run prints node's own tally summed over the files.
* **Not every definition was probed against the pre-existing suite.** 249 mutants were defined. Pass 1 (pre-existing suite, scanned commit) probed 158 of them, chosen so that every FC item and the highest-risk non-FC behaviors came first; probing all 249 against that suite did not fit the time. The other 91 (the lower-value non-FC rows and 22 more FC rows) were probed in pass 3 against the suite after Task 3's first tests, so their kills are credited to "suite after Task 3" and cannot be split between existing and new tests. All 249 have a verdict.
* **Probe integrity.** Every verdict below came from the bundled probe, which enforces a green non-empty baseline, proof the suite ran, exactly-once targets and byte-exact restore. Each target string was also checked to occur exactly once and each mutated file to parse (`node --check`) before probing, so a syntax error could not be scored as a kill. One run was stopped by hand (to cut the definition list); the two clone `src` trees were reset with `git checkout -- src` inside those scratch clones.

## Method summary

* **Pass 1 (mutation, pre-existing suite).** One mutation per behavior from the skill's catalog (remove a predicate, invert a comparison, drop a throw or an `await`, change `"block"`, drop a deny-list entry), written to `.mutation-test/*.toml`, probed against the suite at the scanned commit with none of this plan's tests written.
* **Pass 2 (survivors).** Each survivor got a discriminating assertion, strengthened in place where an existing test meant to cover the behavior (`hook.test.ts`, `failclosed.test.ts`, `validation-failures.test.ts`) and otherwise added under `test/mutation/`. Each was re-probed with the new tests until killed, or recorded as equivalent with a one-line argument.
* **Adversarial pass.** For each Target Unit the expected behavior was derived from `docs/containment.md` ("Generated host settings", "Enforcement coverage matrix", "Fail-closed behavior", "File-edit safeguards", "Budgets"), `docs/repository-onboarding.md` (state diagram, "Validation", "Mapping-mode decision table") and `docs/contracts-and-state.md`, then falsified with inputs the suite did not use. Results are under Findings.

## Findings

### MF-01 Fixed: the reap test's child process exits at start-up, so the test races pgrep

* **Unit.** `test/integration/claude-host.test.ts`, "ends a process that carries the session ID, with its group, and reports one terminated" (`ClaudeHostAdapter.reap`, `src/adapters/host-claude/claude-host.ts`). This is the intermittent failure 01-18 reported once and never reproduced.
* **Oracle.** The test's own premise: a running process carries `--session-id <uuid>`, and reap ends it (`reap` is the resume-time recovery in docs/repository-onboarding.md "Failure and recovery").
* **Violated property.** The child was started as `node -e SCRIPT --session-id ID`. After `-e`, node parses `--session-id` as one of its own options and exits at once with `bad option: --session-id` (exit 9). The process exists for a few milliseconds only, so the test passed when `pgrep` ran before that exit and failed with `terminated: 0` (expected 1) otherwise. Under CPU load it failed on the fifth of eight runs.
* **Verified repro.** `node -e 'setTimeout(()=>{},90000)' --session-id x` prints `node: bad option: --session-id`. A new assertion, that the process is still running 500 ms after spawn, fails deterministically on the old arguments.
* **Fix.** Commit `c06f6eb` adds the assertion (RED), commit `d678833` passes `--` before `--session-id` (GREEN). The expectation `{ terminated: 1 }` is unchanged. The production `reap` is not affected: it targets a host that has been running.
* **Second defect in the same test (found by the clone runs).** The session ID was a constant, and `reap` finds processes by `--session-id` in the whole process table. Two suite runs at the same time (the two probe clones) matched and ended each other's child: 11 of 12 concurrent runs of the test failed. Commit `90dafb1` makes the ID a random UUID.
* **Cost it caused in this campaign.** Eleven reruns of this file in the clone runs before the fix, and a few after it, from the concurrent runs described in O-6.

### MF-02 Open at the campaign, resolved in Resolutions: the launch preflight does not require `sandbox.network.strictAllowlist`

* **Unit.** `src/adapters/host-claude/launch-preflight.ts`, `REQUIRED_KEYS`.
* **Oracle.** docs/containment.md "Generated host settings" shows `"network": { ..., "strictAllowlist": true }`; "Generated settings missing or invalid: the host adapter refuses to launch".
* **Violated property (candidate).** A generated settings file with `strictAllowlist: false` and an empty `allowedDomains` passes `checkLaunchReady`. `allowedDomains` is checked to be `[]`, but `strictAllowlist` is not in the list, so a settings file that is not strict launches.
* **Repro.** `test/containment/failclosed.test.ts`, "when the sandbox network allowlist is not strict" (a `todo` test that currently fails).
* **Why open.** Which keys the preflight must verify is not stated in the documents, and what the host does with `strictAllowlist: false` and no listed domain is unverified. The settings file is generated into the data root, which a contained run cannot write, so exposure needs another failure first. The fix is one entry in `REQUIRED_KEYS` plus the already written test; it needs the owner's decision.

### MF-03 Open at the campaign, resolved in Resolutions: the 2 KiB cap on a document node counts top-level string fields only

* **Unit.** `src/domain/knowledge-validation.ts`, `textBytes`.
* **Oracle.** docs/repository-onboarding.md "Validation", Document nodes row: "each node's text is under a size cap (default 2 KiB)".
* **Violated property (candidate).** Text held in a nested field (an array or an object) of a knowledge-pass node is not counted, so a node can carry more than 2 KiB. The secret scan still covers the whole JSON, so the gap is size (document text copied into the graph, ONB-2), not secrets.
* **Repro.** `test/unit/graph-merge.test.ts`, "counts text held in a nested field of a document node toward the cap" (a `todo` test that currently fails).
* **Why open.** The code comment states the intent as "the UTF-8 bytes of all its string fields". Counting nested strings could reject the real skill's output, which no plan has seen yet (deferred item 5), so the stricter rule needs the owner's decision and one live run.

### MF-04 Open at the campaign, resolved in Resolutions: the hook's shell read check does not see unquoted glob or brace expansion

* **Unit.** `src/domain/hook-decision.ts`, `checkSegment` and `lex`.
* **Oracle.** docs/containment.md coverage matrix row 2 (no reads of secrets, other profiles or the AVARICE store: sandbox `denyRead`, `Read(...)` deny rules, hook path check).
* **Violated property (candidate).** Each word of a read-only command is checked as a literal path. `cat <dir>/re{po,xx}/x`, `cat <dir>/re*/x` and `cat <dir>/rep?/x` are all admitted by the hook although each names a file under the denied root `<dir>/repo` once the shell expands it. The sandbox `denyRead` is the control that stops the read; the hook layer does not.
* **Repro.** `test/mutation/fail-closed.test.ts`, "denies a shell read that names a denied directory through an unquoted brace or glob expansion" (a `todo` test that currently fails).
* **Why open.** Refusing `*?[{` in the lexer would also refuse the legitimate `find . -name '*.ts'` unless quoting is tracked per character, and the matrix gives the sandbox as the enforcing layer. Owner decision.
