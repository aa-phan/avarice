flagged_assumptions:
  - "Choice for GCR-01 (the planner was asked to pick and justify): REFUSE a command whose bound values cannot be shown whole, as privileged:unapprovable; do NOT print full values. Reasons: (1) the event store caps a string at 1,024 characters and an event at 8,192 (Phase 1 decision), so printing full values would still need a refusal past some cap, which makes option (b) option (a) plus new event fields, new storage and a changed approve output; (2) the approval.requested event is redacted on write, so a value holding a secret-shaped text would be shown to the owner differently from what the digest binds, and only a refusal keeps 'what the owner sees is what the approval binds' true without exception; (3) it reuses the one existing refusal rule (privileged:unapprovable, WR-04) and its documented behavior, so no new rule ID, event type or JSON shape appears; (4) the cost is that a command with a long bound value cannot be approved inside a session, and the refusal says the owner can run it at their own terminal, where the attended hook does not apply."
  - "The display caps stay as they are (80 characters per key and per value, 400 for the whole summary). A command is unshowable when any key or value would be cut, the joined summary would be cut, a key or value holds a control character (it would be shown as a space), a value has no printable canonical form, or the secret patterns would redact part of the summary. paramsSummary keeps its clipping as a defence; for an approvable command it never clips."
  - "In an attended session the working directory is a bound parameter (CR-03), so it counts: a privileged command run from a directory whose canonical path is longer than 80 characters is unapprovable there. The reason names the parameter, never its value."
  - "In a run the rule names do not change (04-40 decision): an unshowable privileged command is denied with its usual privileged:<action> rule, one policy.denied is recorded and no approval.requested is written, and the reason says why no approval was asked."
  - "The approval gate (authorizeAction, used by promotion) gets the same rule: it records no request for parameters that cannot be shown whole and denies with privileged:unapprovable. A contract that authorizes the exact parameters still allows the action, because no owner display is involved."
  - "approve.ts needs no change: every request written after this plan carries a summary that is the whole of every bound value. Pending requests written before this plan are not re-checked (accepted, T-04-149)."
  - "The existing hook test 'cuts a long value with an ellipsis for display' encodes the defect and is replaced, as the gap's fix requires; no other existing expectation changes."
