## ADR-001: TypeScript on Node.js with built-in SQLite
- source: /Users/aphan/avarice/docs/decisions/ADR-001-language-and-runtime.md
- status: proposed (Proposed, 2026-10-29)
- decision: Write AVARICE in TypeScript restricted to erasable syntax (Node runs it with type stripping, no build step in development); ship a bundled JavaScript build for distribution. Persistence uses `node:sqlite` (no native dependencies). Minimum supported runtime is Node 22.13; `node:sqlite` experimental status is accepted on 22.x and 24.x and reported by `doctor`. `doctor` imports `node:sqlite`, opens an in-memory database and reads `sqlite_version()`; a bundled SQLite older than the WAL-reset fix (3.44.6, 3.50.7 or 3.51.3 per release line) makes `doctor` refuse to run more than one AVARICE process against a store.
- scope: TypeScript, Node.js, node:sqlite, SQLite, AVARICE CLI, doctor, erasable syntax, bundled JavaScript build, node --test (contract tests under `node --test`). Revisit when: enterprise provides Python but pins Node below 22.13; `node:sqlite` stability changes or removal; `status` misses AC-2.

## ADR-002: AVARICE supplies services to GSD and never orchestrates the loop
- source: /Users/aphan/avarice/docs/decisions/ADR-002-gsd-integration-mode.md
- status: proposed (Proposed; superseded in part by ADR-006 for unattended runs; 2026-10-29)
- decision: AVARICE owns the run envelope (intake, context assembly, run ledger, deterministic verification evidence, authorization records, profile isolation, diagnostics). GSD owns everything between plan and ship. Lifecycle ownership: intake to context ready = AVARICE; context ready to planned = GSD (`/gsd-quick` or `plan-phase`, AVARICE supplies the context pack); planned to implemented = GSD executor (AVARICE observes `state.json` and git); implemented to verified (goal) = GSD verifier; implemented to evidence recorded = AVARICE; verified to PR open = GSD `ship` (AVARICE gates at `ship:pre`, reconciles at `ship:post`); PR open to feedback attempt = AVARICE opens attempt, GSD plans and executes; any to paused = GSD `pause-work` for its session, AVARICE checkpoint for the run. Two integration stages: Stage 1 (AVARICE writes context pack and brief to files, prints the GSD command for attended work, observes via `state.json`, `planning inspect` and git; no GSD extension) and Stage 2 (project-scoped capability, pins `engines.gsd` to the tested minor). AVARICE never retries a step inside a GSD unit, never edits `.planning/` directly, never decides a GSD phase is complete.
- scope: AVARICE, GSD, run envelope, lifecycle transitions, integration Stage 1, integration Stage 2, state.json contract, planning inspect, gsd_run CLI, GSD capabilities, GSD ship gates, HANDOFF.json. Partially superseded by ADR-006 (unattended runs only; the ownership table still holds).

## ADR-003: One local SQLite database per profile, artifact bytes in a separate store
- source: /Users/aphan/avarice/docs/decisions/ADR-003-local-persistence.md
- status: proposed (Proposed; amended by ADR-010 for optional local services; 2026-10-29)
- decision: Each profile has one SQLite database in WAL mode on local storage, opened through `node:sqlite`. Artifact bytes live outside the database in a content-addressed store behind the `ArtifactStore` port; the database keeps only digests and metadata. Backups use `VACUUM INTO`, never a file copy of a live database. Schema migrations are numbered, checksummed and applied one per transaction. `doctor` refuses to open a database on a network mount (detected by `statfs` filesystem type on macOS and Linux, drive type on Windows); profile configuration cannot point `dataRoot` at a network mount.
- scope: persistence, SQLite WAL, ArtifactStore port, content-addressed artifacts, backup (`VACUUM INTO`), schema migrations, network-mount refusal, per-profile data root. Amended by ADR-010: the no-server stance holds for the baseline only.

## ADR-004: Modular monolith with ports only at realistic migration boundaries
- source: /Users/aphan/avarice/docs/decisions/ADR-004-modular-monolith-and-ports.md
- status: proposed (Proposed; amended by ADR-010; 2026-10-29)
- decision: AVARICE is one package run as short-lived commands plus a per-run supervisor. Responsibilities are modules separated by import rules (architecture.md owns the module list). Ports exist only where a second implementation is expected within the roadmap or the provider must be swappable per environment (contracts-and-state.md owns the port list). Policy is not a port. MCP is not an internal transport; a stdio MCP server is a thin optional wrapper over the same application services.
- scope: package structure, modules, ports, import rules, MCP, policy. Revisit when: a port gains no second implementation within two slices after its planned slice (merge it back); two independent consumers need the same capability over the network. Amended by ADR-010 for baseline-only no-server stance.

## ADR-005: Deny-by-default privileged actions, parameter-bound approvals, hard profile separation
- source: /Users/aphan/avarice/docs/decisions/ADR-005-policy-approvals-and-profiles.md
- status: proposed (Proposed; 2026-10-29)
- decision: (1) Every action is classified `read`, `local-write` or `privileged` (FR-12); classification table lives in code. (2) Privileged actions are denied unless a matching approval exists bound to run, action and parameter digest: either a single-use approval record with expiry, or the run contract when it authorizes that action with its parameters; approving a plan never creates action approvals (FR-13). (3) Policy rules come only from built-in defaults, the user profile and (enterprise) the organization policy file; retrieved content and tool output are never policy sources (FR-14). (4) Precedence: organization, then built-in defaults, then user, then repository; lower layers can only add restrictions in an enterprise profile. (5) Each profile has its own data root, configuration, credential references, caches, logs and artifacts; a run is pinned to one profile at creation; no fallback to another profile. (6) Host enforcement uses a PreToolUse hook calling `avarice hook pre-tool-use`, denying privileged shell commands without approval; AVARICE documents that the host enforces the hook only while installed and not disabled.
- scope: authorization, action classification, approvals, policy sources and precedence, profile isolation, PreToolUse hook. Revisit when: an enterprise provides a policy decision service; the host exposes a supported non-bypassable policy hook.

## ADR-006: Unattended runs delegate bounded GSD units through contained headless invocations and route every GSD pause
- source: /Users/aphan/avarice/docs/decisions/ADR-006-unattended-delegation.md
- status: proposed (Proposed; supersedes in part ADR-002 for unattended runs; 2026-10-29)
- decision: (1) A per-run AVARICE supervisor starts headless host invocations, one GSD unit per invocation, inside the containment of containment.md; it never drives GSD steps inside a unit. (2) MVP unit is `/gsd-quick --validate --text "<contract-derived task>"` for one work item; phased work uses `/gsd-autonomous --only <N>` with `workflow.auto_advance=true` after the integration suite tests the possible double-execute path. (3) Before the first invocation AVARICE sets run-specific GSD config in the run worktree via `gsd_run config-set`: `workflow.text_mode=true`, `gates.execute_next_plan=false`, `gates.confirm_transition=false`, `workflow.windows_enforce=true`, `audit.enabled=true`; never `discuss --auto` or `discuss-phase-assumptions --auto`; reversibility gates stay on. (4) Outcome is classified deterministically from stream-json `result`, `permission_denials`, `WAITING.json`, `state.json`, `HEAD` movement, STATE.md `needs_human` entries and VERIFICATION.md status; an invocation ending without progress and with a question is a GSD pause. (5) A GSD pause is answered only by a validated human decision or an authorized contract default; `checkpoint:decision` without `auto_select`, any `blocking-human`, any `human-action` and executor Rule 4 always go to a human; answers delivered with `claude -p --resume <session>`. (6) AVARICE adds integrity gates (reject verification overrides added during the run, treat node-repair PRUNE as a decision, block files outside writable scope, compare test inventories, require skipped-test ledger empty or justified), run after each unit in Stage 1 and as blocking GSD gates in Stage 2. (7) Unattended endpoint is `ready_for_review` (branch in run worktree plus evidence package); push and draft PR happen outside the contained invocation, by AVARICE, only when the contract authorizes; GSD `ship` only in attended runs.
- scope: unattended runs, supervisor, headless `claude -p`, GSD config, outcome classification, GSD pause routing, integrity gates, ready_for_review endpoint. Supersedes ADR-002's "Stage 1 manual handoff only" part and its "never orchestrates the loop" title for unattended runs (supervisor starts units and retries a crashed invocation once, CON-16). Revisit when: GSD ships headless mode, pause signal or budgets; Claude Code changes `dontAsk`, `--permission-prompts` or `--max-budget-usd` meaning; more than 10% `inconclusive` endings in the benchmark.

## ADR-007: Measure test strength with a mutation gate; reuse the adversarial-mutation-test skill, probe in Node
- source: /Users/aphan/avarice/docs/decisions/ADR-007-mutation-gate.md
- status: proposed (Proposed; 2026-10-29)
- decision: (1) Gate G4 gains an optional mutation gate over changed lines using a deterministic, model-free mechanical mutant set (comparison and boundary flips, boolean negation, arithmetic operator swaps, constant and return-value replacement, removed early returns or guard clauses); each mutant must be killed or explicitly accepted as equivalent. (2) AVARICE ships a Node mutation probe written independently from the documented behavior of `mutation-probe` (same `mutants.toml` format, same four verdicts KILLED/SURVIVED/NO-RUN/HARNESS-ERROR, same exit-code meaning, same integrity refusals); installed `mutation-probe` may be used through the same adapter; no plugin code copied. (3) The probe runs outside the contained invocation in a disposable clone of the run worktree at the verified revision, in the same OS sandbox configuration as other checks; it never mutates the run worktree or the user's checkout. (4) The skill is reused unchanged for a `harden` work item type (one contained GSD unit; test paths writable, all non-test paths read-only; narrowed serial scope; no Workflow fan-out); skill-proposed mutants and adversarial findings are `model-review` evidence supplementing, never replacing, the mechanical set. (5) Survivors after the repair budget become a decision record of class `repeated_failure`; `NO-RUN` is `inconclusive`, never scored as a survivor.
- scope: gate G4, mutation testing, Node mutation probe, `harden` work items, adversarial-mutation-test plugin 0.35.0 (DecentraLicense not reviewed). Revisit when: plugin publishes prebuilt probe or npm package; license reviewed and permits vendoring; equivalent-mutant escalations exceed 20% of mutation-gate escalations.

## ADR-008: GSD maps and plans; AVARICE onboards in a contained staging worktree and records provenance
- source: /Users/aphan/avarice/docs/decisions/ADR-008-repository-onboarding.md
- status: proposed (Proposed; 2026-10-29)
- decision: (1) AVARICE owns operational and trust onboarding; GSD owns semantic mapping and planning content; enterprise systems stay authoritative for their records. (2) All GSD onboarding work runs in a staging worktree at the recorded revision; each top-level GSD workflow runs in one contained headless invocation with a read-only command allow list and the fail-closed hook; sandbox writes only the staging `.planning/` (knowledge pass: only `.avarice-knowledge/`) and no network; commits off (`commit_docs=false`, `git commit` not allowed) unless the contract authorizes promotion by commit. (3) AVARICE runs `init onboard` only in staging, runs `stamp-codebase-map` itself after fast maps, and records mode, scope and completeness in its own project record. (4) Planning initialization uses `/gsd-ingest-docs --manifest --mode new`, never `/gsd-new-project --auto`. (5) A versioned project record in the ledger references GSD artifacts by path, digest and stamp and holds only operational metadata; accepted artifacts reach the user's checkout only through explicit promotion. (6) A `GsdOnboarding` port pinned to GSD 1.17.x wraps these operations. (7) Index stage (on by default) builds GSD intel and the GSD-managed graphify graph in staging (ONB-13); graph build is a sandboxed command with no model call, intel refresh is a contained invocation; project record keeps each index's build commit; context assembly queries indexes before whole files (FR-20); failed index build drops that index and never blocks activation; a knowledge pass adds document nodes for stable documents (ONB-14) in one contained invocation merged into the graph; GSD phase files join only once incremental refresh exists (ONB-15).
- scope: repository onboarding, staging worktree, GsdOnboarding port, project record, promotion, index stage, knowledge pass, graphify 0.9.53 optional dependency. Revisit when: GSD adds onboarding loop points or headless mode or records scope/completeness in its stamp; GSD relocates `.planning`; mapping cost exceeds the onboarding budget in the brownfield benchmark (AC-14).

## ADR-009: Resolve credentials through a broker port over existing stores
- source: /Users/aphan/avarice/docs/decisions/ADR-009-credential-broker.md
- status: proposed (Proposed; 2026-10-30)
- decision: (1) `CredentialProvider` is a broker that resolves a reference at the moment of use and stores no secret value; AVARICE runs no secrets server. (2) Accepted references are `delegated:<cli>`, `keychain:<service>` and `cmd:<approved helper>`; `env:` is not an accepted reference type in any profile (a resolved value may still be passed into the environment of one of AVARICE's own privileged subprocesses). (3) Every resolution attempt, including failures, is recorded as a `credential.resolve` event (SEC-8) with reference, purpose, calling module, profile, run and invocation IDs, outcome (`resolved`, `denied`, `unavailable`) and duration; never the value, its length or any digest. (4) A server-backed store (Vault, OpenBao, 1Password) may be added later as one more adapter behind the same port (for example `vault:<mount>/<path>#<field>`) emitting the same event; until then Vault is reachable via `cmd:` with an approved helper.
- scope: credentials, CredentialProvider port, SEC-2, SEC-8, credential audit events, `doctor` failing on `env:` references. Revisit when: personal-extended profile has more than one machine or remote worker needing the same secrets; employer mandates Vault or another server-backed store; a workflow needs dynamic short-lived credentials.

## ADR-010: Keep the serverless baseline; allow an optional local-services deployment
- source: /Users/aphan/avarice/docs/decisions/ADR-010-serverless-baseline-local-services.md
- status: proposed (Proposed; amends ADR-003 and ADR-004, whose no-server stance now holds for the baseline only; 2026-11-01)
- decision: (1) The baseline stays serverless (NFR-1 unchanged): every MVP capability works with no container runtime, no daemon and nothing listening on a port. (2) A local-services deployment is a supported option: the same service adapters planned for a homelab may run on `localhost` through Docker Compose, Podman or native installs; only the endpoint differs. (3) The personal-extended profile may use it freely; an enterprise profile only when the onboarding questionnaire confirms containers or daemons are permitted (question 25). (4) Each service stays optional; a stopped or missing local service degrades like an unreachable homelab service (ledger read-only and local drafts; artifact writes fall back to local disk only where the profile allows; no run starts without enforcement). (5) Services never replace a system of record in an enterprise profile (no local service holds company credentials, acts as package source, or records work in place of the company tracker). (6) Services bind to `localhost` only; AVARICE changes no DNS resolver, proxy or machine-wide package setting. (7) A service is added only for a measured need (slice 6 triggers apply unchanged; further triggers: live dashboard, or a knowledge service shared by several sessions).
- scope: deployment topology, optional local services, enterprise profile limits, slice 6 services. Revisit when: employer known and questionnaire permits containers; a need only a long-lived service meets (concurrent writers, live dashboard, shared knowledge service); local-services test matrix too costly (then support only homelab endpoint).

## ADR-011: Ship a static, read-only dashboard in the MVP
- source: /Users/aphan/avarice/docs/decisions/ADR-011-static-dashboard.md
- status: proposed (Proposed; narrows the dashboard non-goal in requirements.md; 2026-11-01)
- decision: (1) `avarice dashboard` renders one self-contained HTML file from the profile's ledger and opens it in the default browser (FR-26); inlined styles and scripts, no network loads, no server or listening port. (2) Read-only: shows runs and states, work items, open decisions, gate results and evidence summaries, budgets and spend, onboarding records with index freshness, recent events; answering a decision stays in the CLI (`avarice decide`). (3) `avarice dashboard --watch` regenerates the file when the ledger changes while the command runs and the page reloads itself. (4) File written under the profile's data root with mode 0600, never into a repository; passes through the event redactor (SEC-3); one profile only (SEC-1). (5) A served, multi-client dashboard stays outside the MVP (possible with the coordination service or a local-services deployment per ADR-010).
- scope: dashboard, observe module, FR-26, AC-15. The requirements.md non-goal now reads "A dashboard that needs a server or a listening port in the MVP. The static dashboard in FR-26 is in scope" (already consistent). Revisit when: rendering 1,000 runs misses AC-15; two machines write the same ledger (slice 6c); users need to answer decisions from the page.

## ADR-012: Hold code to a repository-owned, machine-checkable architecture model
- source: /Users/aphan/avarice/docs/decisions/ADR-012-architecture-model.md
- status: proposed (Proposed; amends ONB-2 through requirements.md; 2026-11-01)
- decision: (1) A repository may declare an architecture model in `.avarice/architecture.json` (FR-25), committed and versioned by git; it restates the design in checkable form and does not replace GSD's prose. (2) The model lists components (ID, kind in service/module/library/process/datastore/interface/external, path globs), edges (kind in imports/calls/reads/writes/publishes/subscribes; data edges name the contract symbols that cross), and shared resources (each with a UUID, one identity across repositories of a project group, FR-21). (3) AVARICE drafts the first model deterministically from the code graph (top-level packages and directories become components, observed imports become edges) as a proposal in the onboarding staging worktree; it becomes the model only through promotion and user approval. (4) An `architecture-model` check compares the code graph at a revision with the model and reports: component whose paths match no code; code outside every component and declared exclusions; import between components with no declared edge; contract symbol on an edge the code does not define. It runs at G4 when declared; in G2 a new cross-component import with no declared edge is an AUT-17 finding. (5) The agent cannot change the model: `.avarice/**` is a protected path in every contract; a finding needing a design change becomes a decision. (6) ONB-2 is amended: a repository-owned model the user approves is not an AVARICE index; AVARICE stores only its path, digest and check results.
- scope: architecture model, `.avarice/architecture.json`, architecture-model check, FR-25, G2/G4, AUT-17, ONB-2. Revisit when: findings dominated by stale-model noise; GSD adds a machine-readable architecture artifact.
